## Rationale

Rides have power from a single-sided (left) crank meter since
2026-10-24. Strava marks real power with `device_watts = true`. D27
anticipated this: "Revisited only by addendum if a direct-measure power
meter appears." This revision lands the per-second `watts` stream and a
one-second grid with an explicit fill rule. Metrics (NP, power curve,
EF, decoupling, TSS) are a later phase.

Named improvement over the Strava screen (the §3 non-goal requires
one): Strava shows a power trace with no statement of which seconds were
measured. The grid classifies every second of a ride as observed, held,
stopped, or missing, and reports per-ride coverage.

## What the data showed (2026-11-02, read-only)

Six rides have `device_watts = true`: 33,080 samples, all from one head
unit. 37,585 grid seconds once the time stream is expanded.

- **NULL watts: 0 samples.** Missing seconds: 239 time-stream gaps,
  4,505 seconds, nearly all at stops. 0 W: 3,896 samples (11.8%).
- One-second recording with pause gaps, not smart recording: 32,835 of
  33,074 steps are 1 s. Time starts at 0, strictly increases, has no
  duplicates. Arrays are aligned and not downsampled.
- Long 0 W runs have cadence near 0 at 3–8 m/s: coasting. 0 W at
  cadence ≥ 40 and speed ≥ 2 m/s never lasts longer than 2 s.
- `device_watts` is also true on 90 **runs**. The rule "trusted only
  when `device_watts = true`" therefore does not by itself select rides;
  ride type is a separate required filter.

### Known limit: the form of a power dropout is unobserved

No sustained 0 W while pedaling appears in these rides, so the
stop-and-report condition did not fire. A real dropout may simply not
have occurred, so these rides cannot show what one looks like. **A
future dropout that arrives as 0 W would be labeled `observed`.** Ten
isolated 0 W seconds inside power, with pedaling on both sides, cannot
be told apart from real values; their size is negligible. The owner
ruled: record the limit, no 0 W detection in this phase. The limit is
repeated in the model YAML.

### Strava's summary fields are not a cross-check

`average_watts` is 2–6% above the mean of the stream samples on all six
rides. `weighted_average_watts` is below `average_watts` on all six,
which normalized power on the same samples cannot be. These two fields
disagree with the stream and with each other. **They must not be used
as a cross-check in the metrics phase.**

## New decisions

| # | Decision | Final value |
|---|----------|-------------|
| D31 | Ride power fetch | Rides enter `raw_strava.streams` when `device_watts` is literally true, the type is a D23 ride type (no e-bikes), moving time ≥ `STREAM_FETCH_MIN_MOVING_MINUTES` (the same 20-minute gate), within the D5 window, and the row is absent or `failed`. **No HR requirement** (D25: HR never gates rides). `success` and `unavailable` stay terminal, so a successful ride row with no watts in its payload is never re-selected. Rides use `RIDE_STREAM_TYPES`: the five run keys + `distance` + `watts`. `STREAM_TYPES` and every run request are unchanged, and `stream_types_requested` records the keys actually sent. Selection lives in the daily `sync-streams`, runs first, one shared batch cap, the existing exit-3 contract. |
| D32 | One-second power grid | `stg_strava__ride_power_samples` (activity × sample; `success` rows, `device_watts` true, `ride_sport_types`) → `int_ride_power_grid` (activity × second, `t_sec` 0 to the ride's last `t_sec`) → `int_ride_power_coverage` (activity). Columns: `watts_observed` as received, `watts` for downstream use, `fill_reason` ∈ observed / held / stopped / missing, `distance_m` observed only. NULL means missing, never zero; coasting is a real 0 W. Coverage = (observed + held) / (total − stopped), no threshold in this phase. Vars: `power_hold_max_gap_s` 3, `power_stopped_speed_mps` 2.0 (owner ruling below; the first design had 1.0). |

### Fill rule (D32)

Applied to each run of consecutive seconds with NULL `watts_observed`,
first match wins:

1. Run length ≤ `power_hold_max_gap_s` and a prior observed value exists
   → `held`, `watts` = last observed value.
2. No observed row before or after the run → `missing`.
3. Speed across the run, from the bounding rows' distance and `t_sec`,
   is below `power_stopped_speed_mps` → `stopped`, `watts` NULL.
4. Otherwise → `missing`, `watts` NULL.

Confirmed readings:

- First match wins, so a short run at the end of a ride is `held` and a
  short run at the start is `missing`.
- A time gap of G seconds is a run of G−1 seconds.
- Bounding rows have non-NULL `watts_observed`. A sample with NULL watts
  never bounds a run.
- A NULL distance on a bounding row means speed is unknown, so the run
  is `missing`, never `stopped`.
- Coverage is NULL when total − stopped is 0.

### Owner ruling: `power_stopped_speed_mps` = 2.0 (2026-11-02)

The owner reviewed the 14 gaps that a 1.0 m/s threshold classified as
`missing` (87 seconds), before the grid was built, and set 2.0.

All 14 show one pattern: coasting at 0 W and slowing to 1.3–3.4 m/s,
then a 5–10 s time-stream gap, then 5.4–7.2 m/s, with 13 of 14 already at
257–458 W. Speed across the gap (1.03–1.88 m/s) is the deceleration and
re-acceleration averaged into a short stop. None looks like a dropout
while riding, which would show speed across near riding speed.

| Threshold (m/s) | Stopped (s) | Missing (s) | Coverage |
|---|---|---|---|
| 1.0 | 4,264 | 87 | 0.9974 |
| 2.0 (adopted) | 4,351 | 0 | 1.0000 |

**Limits of this value.** It is a judgment call: no gap in these rides
exceeds 1.88 m/s, so no real dropout sets the upper bound. Coverage of
exactly 1.0 on these rides means no gap counted as a dropout. It does
not show that the meter never dropped out, and it adds to the known limit
above. A real recording gap on a very slow climb, under 2 m/s, would be
labeled `stopped`.

## Amended decisions

- **D15 (stream eligibility).** Gains a ride branch, limited to D31.
  The run branch is unchanged. The rest of the deferred ride-stream work
  stays deferred (rolling speed, stop-loss, pedaling-time share); the
  other rides stay unfetched.
- **D27 (power exclusion).** Power is modeled only from the `watts`
  stream of rides with `device_watts = true`. Estimated `average_watts`
  and `kilojoules` stay raw-JSONB-only. No estimated-watts row may reach
  a power model.
- **D26 (cadence) is not amended.** `cadence` is not in
  `RIDE_STREAM_TYPES`.

## Exceptions to earlier rules

- **Owner exception to v2.0's "no running model changes" rule.**
  `int_run_stream_samples` and `int_run_stream_state` read every
  `raw_strava.streams` row with no sport filter, so ride rows would have
  entered them and `int_band_window_samples`. All consumers start from
  run candidates, so marts would not have changed, but the views'
  contents would. The owner ruled for a sport filter in those two models
  over leaving ride rows in run views. It lands in its own commit, before
  any ride stream rows exist, red first. All three views join the
  invariance comparison and must come out identical.
- **"Payloads are deliberately unstaged" (v1.2 follow-up).** Ride power
  is staged because the spec asks for a sample-grain staging model.
  Staging may already read sources, so the layer matrix does not change.
  Run payloads stay unstaged.

## No backfill flag or target

The first design had a one-time `backfill-ride-watts` target. The owner
removed it. No ride has a stream row and every new ride row requests
`watts`, so a "stored streams lack watts" selector could never match a
ride. No runs are pending a fetch (0 no-row, 0 failed on 2026-11-02), so
plain `make sync-streams` fetches the six rides and keeps run streams
out of the invariance window. New rides arrive the same way.

## Invariance

Before and after the change, bidirectional `EXCEPT ALL` over the 12
marts, 6 core tables, and 3 running views (`int_run_stream_samples`,
`int_run_stream_state`, `int_band_window_samples`). All must be
identical. The baseline is taken on main before any code change. No sync
other than the ride fetch runs between the snapshots.
